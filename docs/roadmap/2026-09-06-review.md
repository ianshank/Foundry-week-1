# Engineering review — 2026-09-06

A four-discipline review of the repository at `main` (`6d27c4d`) and of the open
pull request #5, done to answer one question: **what is the best next step in
code development?**

Every finding below was reproduced against the tree, not inferred from reading.
Claims that could not be reproduced are marked as such. Where a reviewer was
wrong, the correction is recorded rather than dropped — a review that only
publishes its hits is a review you cannot calibrate.

Reviewers: an implementation audit, a test-and-CI audit, a product/architecture
audit, and an independent read of PR #5, each run without sight of the others,
then cross-checked by hand.

## 1. The finding that orders everything else

This repository exists to detect one failure mode: **a system that reports a
non-result as a pass.** That is what `planlint` exit 2 is for, what the
three-valued scorer contract is for, and what the whole verifier probe is
designed to catch a language model doing.

The code does this correctly. The week's own paperwork, on the open pull
request, does not.

`evidence/05-verdict.md` on PR #5 recommends **"proceed to a Week 2 hosted
twin"** — a recommendation that costs an Azure subscription, a Foundry project,
role assignments and a reachable remote MCP endpoint. Its contract table marks
`planlint exit 1 → FINDINGS` as **preserved: Yes**, citing
`evidence/03-mcp-selfcheck.json`. That file records, for the findings case:

```
"expected_verdict": "FINDINGS",
"actual_verdict": "PASS",
"matched": false
...
"all_expected": false
```

Be precise about what this is and is not. It is **not** a wrapper defect. The
chosen target contained no specs (`"specs_checked": 0`), so `planlint`
legitimately exited 0 and the wrapper correctly reported PASS. The fixture was
wrong, not the code. What the verdict does is upgrade an **untested** contract
row to a **verified** one, on the strength of a file whose own summary field
says the run did not meet expectations.

That is the shape of failure this repository was built to detect, occurring in
the artifact the repository exists to produce. It is the strongest available
argument for the plan in section 6: the next step is not more code.

Further claims in the same document are unsupported by anything committed:

| Verdict claim | What is committed |
|---|---|
| Bake-off winner per prompt: C (Ollama), all three prompts | Slots A, B and D were never run. The matrix's own margin column reads "Only model tested." |
| "Models that mishandled exit 2: None" | The exit-2 column is blank for every slot, including C. No model was ever shown the exit-2 fixture. |
| All four agent probes passed | None were run. `traces/` holds one capture; `snippets/`, which step 4.5 requires, holds only a README. |
| Peak VRAM 9.0 GB, total latency ~15,000 ms, "measured via script" | The probe scripts capture no VRAM at all, and the one committed measurement records 47,859 ms. |

The scale of the gap is worth stating plainly. The runbook asks for four model
slots across three prompts, twelve cells before the optional exit-2 variant.
What exists is **one model, one prompt, one run** — `ollama:qwen2.5:14b` against
the verifier fixture, which the deterministic screen scored HELD on the basis of
its declared verdict line. That is roughly one cell in twelve. Half the tool
surface has no field evidence at all: `score_run` appears in no evidence file,
because the demo eval aborted before writing a sink artifact.

`evidence/02-bakeoff.template.md` on the branch is more honest than the verdict
built from it: an HTML comment states plainly that D was dropped and that A and
B are blank because only Ollama was evaluated. But its four completion boxes are
all ticked, including *"Matrix complete (no blank cells; 'dropped' is an answer,
blank is not)"*, against a matrix with six blank cells.

To be fair to the work: the three stop conditions are recorded correctly as not
fired, and one of them is machine-enforced. BLOCKED is derived from the exit
code rather than from parsing stderr strings, which is exactly the distinction
the runbook warns against getting wrong. Where the week did run something, it
ran it properly.

One incidental result deserves promoting, because it is the most interesting
thing in the evidence directory and nothing currently cites it. The baseline
capture shows the existing eval harness *refusing to run*:

```
ValueError: judge_calibration.calibration_artifact_id is required to gate
on ['helpfulness']: a judge's participation in gating must be traceable to
the calibration run that authorised it
```

That is the incumbent enforcing exactly the discipline this spike is evaluating
Foundry against — declining to produce a gated result it could not trace to an
authorising calibration run. It is also why no sink artifact exists, which is
what makes the scoring change on PR #5 unsupportable. Both the strongest
argument for the existing harness and the blocker on half the week's evidence
are the same two lines of output.

**None of this makes the week a failure.** The runbook is explicit that stopping
early on a stop condition counts as a success. A verdict reading *"bake-off
bench only — one model tested, comparative claim unsupported"* would be a
legitimate, defensible outcome. A verdict reading *"proceed, spend the money"*
on the same evidence is not.

## 2. Code defects, reproduced

Four defects were reproduced against the working tree. One breaches the stated
contract; three are robustness or operability faults.

### 2.1 A NUL byte in a model-supplied path escapes as an exception

The contract's first invariant is *an exception is not a verdict*. This is the
one place it does not hold:

```
$ PLANLINT_TARGET=... PLANLINT_ALLOWED_ROOTS=... python3 -c \
  "from foundry_spike_mcp.planlint import lint_openspec; lint_openspec(target='/allowed/x\0y')"
ValueError: embedded null byte
```

`guards.check_target` calls `Path.resolve()`, which raises `ValueError` on an
embedded NUL before any guard can refuse it. `score_run` raises the same way on
both `run_id` and `artifact_path`. Over MCP this surfaces as a protocol error
with no `verdict` field at all — precisely the state the contract says must
never reach the model. A 5,000-character path is handled correctly, so this is
about the NUL specifically.

**Fix:** catch `ValueError` in `check_target` and map it to
`BLOCKED / guard_rejected: invalid_path`. Roughly five lines plus a test.

### 2.2 `make selfcheck` fails in the configuration the repo documents

`.env.example` documents an unset `PLANLINT_ALLOWED_ROOTS` as the fail-closed
default, in which case the allow list falls back to `PLANLINT_TARGET`. The
self-check's blocked case creates a temporary directory and appends it to that
variable — but when the variable is unset there is nothing to append to, so it
*replaces* the fallback with the scratch directory alone. Reproduced:

```
pass -> BLOCKED guard_rejected
  target_outside_allow_list: /home/user/Foundry-week-1 is not under
  any of ['/tmp/foundry-spike-blocked-awt5s59w']
```

`NEXT_STEPS.md` carries this as an open finding described as the tool *widening*
its own guard. It narrows it, and in the documented default configuration the
step-3 self-check cannot pass at all. Existing tests miss it because they always
set the variable.

**Fix:** stop mutating `os.environ`; append the scratch directory to a config
object and pass it through `run_verb(config=)`, a seam that already exists.

### 2.3 A valid findings payload is neither bounded nor redacted

`FOUNDRY_SPIKE_STDOUT_LIMIT` and `guards.clean` are applied only in the branch
that handles stdout it *could not parse*. Output that parses as valid JSON is
stored raw. With the limit set to 100 bytes, a fake binary emitting valid JSON
on exit 1 returned **4,508,904 bytes** of findings, with
`findings_parse_error` and `stdout_excerpt` both null.

The size is the smaller half. The same branch is where `guards.redact` runs, so
**a credential appearing inside valid JSON output is never scrubbed** — it goes
back to the model and into any trace built from the result. `SECURITY.md` lists
"credentials in output" as a controlled surface, redacted then truncated in that
order. That control covers only the unparsable path.

The verdict itself stays correct, so this is not a contract breach. It is a
security and context hazard, and hosting turns the size half into a wire
problem as well.

### 2.4 The secret scanner crashes on a path outside the repository

`python scripts/scan_evidence.py /tmp` ends in a `ValueError` traceback from
`Path.relative_to`, despite the script advertising positional targets. A gate
that crashes on an unexpected argument is a gate someone will route around.

### 2.5 Also confirmed

`make validate` is red immediately after `make setup`: `coverage` is not in the
`[dev]` extras, so the `coverage` target fails on a fresh clone. CI installs it
separately and is therefore green, which is how this survived.

## 3. Test and CI quality

The suite is good, and better than its reputation in `NEXT_STEPS.md`. It passes
(234 tests without the SDK installed, 243 with it), `ruff` and `mypy` are clean,
and the four-way CI job split is a genuinely well-reasoned design: each job
certifies a different claim, which is why the transport job exists at all.

The gaps that matter:

- **"Policy is not configuration" has no test.** This is the repository's one
  stated architectural opinion — that `guards.py` reads no environment variable,
  so an allow list cannot be widened by setting one. Nothing asserts it. A
  parametrized test that sets plausible variables and asserts refusals are
  unchanged, plus a static check that `guards.py` imports no `os`, is about ten
  lines and closes the only invariant with zero coverage.
- **A parsed payload contradicting its exit code is untested.** `verdicts.py`
  states that a payload never overrides an exit code; exit 0 with non-empty
  findings is not exercised. The behaviour is correct today and unpinned.
- **Several exception handlers are unreached** — the `FileNotFoundError` and
  `OSError` paths around execution, `ConfigError` inside `score_run`, and the
  walk's `RecursionError`. All verified correct by hand; none pinned.
- **Coverage is measured without the SDK,** so `server.py` contributes zero to
  the floor and a transport regression is invisible to it. Coverage is 88%
  without the SDK and 92% with; the comment in `pyproject.toml` says 91%.
- **The declared SDK floor cannot run its own smoke suite.** `mcp>=1.2` is
  advertised, and mcp 1.2.0 installs and imports fine here. But the smoke test
  resolves a 2.x module path at import time, so under `REQUIRE_MCP=1` the suite
  errors during collection on 1.2.0 and silently skips without it. The 1.x path
  is otherwise verified only against a stub whose `.tool()` is an identity
  function, and which is never passed to `build_server()`. Either fix the loader
  test or narrow the declared floor; advertising a range you cannot test is the
  weaker of the two options.

## 4. Documentation drift

Six contradictions, all reproduced. Two are live risks; four are tidiness.

**Live:**

0. **The repository default branch is still the stale prep branch.**
   `claude/foundry-toolkit-spike-prep-d92qfh` — the branch PR #1 was merged
   *from* — is still the default, not `main`. This is why the three open
   dependabot pull requests target it: `dependabot.yml` sets no `target-branch`
   and inherits the default. Any pull request opened without an explicit base
   goes to a branch nobody develops on. The previous revision of `NEXT_STEPS.md`
   already flagged this; it is still open.

1. **`.gitignore` protects the wrong path.** It ignores `mcp/mcp.json`, but the
   directory was renamed `mcp_server/`. `git check-ignore mcp_server/mcp.json`
   returns nothing: the file the runbook tells the operator to fill with real
   paths and possibly a GitHub token is committable today. PR #5 does not fix
   this.
2. **The bake-off template cites a gitignored path** for its headless
   transcripts (`traces/raw/<timestamp>-02-verifier/`). This is the exact defect
   `NEXT_STEPS.md` records as fixed under finding #10.

**Tidiness:**

3. `snippets/README.md` says `make scan` does not reach that directory; the
   scanner covers it by default.
4. The outcome vocabulary differs across three documents: the decision record
   offers keep / bench-only / drop, the verdict template offers proceed / stop
   at bench, the README says sidecar or not.
5. "Four evidence files" in the README and runbook; the decision record cites
   six, and the baseline script writes three more.
6. The decision record's fourth "keep" criterion — that the Playground gives a
   faster read than the existing bench — has no field anywhere in the verdict
   template. The criterion the record itself flags as *"most likely to be
   answered generously"* is the one with nowhere to answer it.

**Correction to a reviewer.** One audit reported that
`configs/probes/system-prompt.md` lacks both the tool-authority text and the
`{{target}}` variable that runbook step 4.2 requires. The claim is false in both
halves. Lines 18–24 carry all three required statements in substance: exit codes
are authoritative, the agent may disagree in prose but may not restate a nonzero
exit as a pass, and exit 2 is neither. The variables live in
`configs/probes/agent-probes.md`, which holds the per-run user prompts; the
system prompt is pasted once per slot and correctly carries no target.

Recording this matters more than the finding it retracts. A review that
publishes only its hits gives you no way to calibrate the ones you cannot check
yourself.

## 5. PR #5 — disposition

63 files, +2,799/−692, mixing three unrelated kinds of change. Independently
measured on the branch: 325 tests collected, 321 passed, 4 skipped, 90% branch
coverage. The published counts disagree with each other and with that
measurement — the PR body says 327 tests and 93%, `NEXT_STEPS.md` on the branch
says 311 and 94%, and three other files say 94%.

What it actually contains:

| Kind | Content | Recommendation |
|---|---|---|
| **Evidence** | `evidence/00-*`, `03-mcp-selfcheck.json`, the trace and index, session tracker, the verdict | **Land first, after corrections.** This is the week's deliverable. |
| **Contract change** | `scoring.py` schema pin, and the tests changed to match | **Hold.** See below. |
| **Scaffolding** | probe decomposition, seven new test directories, extra skills and agents, editor and type-checker config | **Trim hard or drop.** |

Three things argue against merging as-is:

**The scoring change pins a schema no artifact supports.** `scoring.py` now
requires a root `results` list and blocks the whole run if any single record is
malformed. `NEXT_STEPS.md` on `main` made pinning conditional on a real sink
artifact. No such artifact exists: `evidence/00-demo-eval.txt` shows the demo
eval raising `ValueError` before writing one, because the harness refuses to
gate on a judge with no calibration artifact. Seven contract tests were deleted
to match the new shape (22 → 19), with no entry in `decisions/` — which the
repository's own contract-guard skill names as the one thing you may not do.
Under `main`'s tolerant walk, an unexpected shape produced data plus a note.
Under the pin, it produces a refusal and nothing.

**The coverage floor was lowered while the change advertised a gate.**
`pyproject.toml` still reads `fail_under = 85`; CI now passes
`--fail-under=80` on the command line, which overrides it.

**Roughly a third of the new tests exercise new behaviour.** The rest assert
that Python is at least 3.10, that the README is non-empty, that functions are
callable, or re-run cases already covered in `mcp_server/tests/`. Net new is
about 90 tests, not the 327 claimed. `requirements.txt` is a Windows `pip
freeze` in UTF-16LE with CRLF line endings and an editable VCS reference —
unusable as written.

The head commit's CI is not green; the latest run reports `action_required`.

## 6. What follows

The full plan, with owners and effort, is in [`NEXT_STEPS.md`](../../NEXT_STEPS.md).
Its shape, in one paragraph:

Close the live risks first, because they are minutes of work and one of them is
a credential path and another is a default branch pointing at a branch nobody
develops on. Split PR #5 so the week's evidence is not held hostage by a
refactor. Then spend half a day making the verdict decidable — one real sink
artifact, an exit-1 fixture, an exit-2 trace, a second model, the four agent
probes — because that converts an unsupportable "proceed" into a defensible
verdict in either direction, and it is the only work on this list the week
actually asked for. Fix the reproduced defects, which are hours rather than days
and all sit on code anything would carry into a week 2. Stop investing in
scaffolding.

The strategic reading is unchanged from what the repository already argues: the
stdio server does not carry into a hosted week 2, the tool contract does, and
the contract is in good shape. The decision about whether to spend on week 2
should be made against evidence that exists.
